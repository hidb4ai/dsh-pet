# 控制 token 用量

[English](../../en/guides/token-budget.md) · 简体中文 · [文档首页](../README.md)

用小窗口处理眼前的对话；确实需要旧事实时再开启长期记忆，并把后台处理的开销单独算清。

## 先限制近期上下文

本机记忆首次设置会选择 **近期 4 轮、近期正文 6000 字节、召回正文 4096 字节**。已有绑定保留用户调整值。原生聊天默认带最近 10 轮。

近期预算选择连续、完整的双方问答。字节预算设为 0 表示只按轮数限制，不是完全不带历史；不需要近期历史时，将轮数设为 0。这些限制是 UTF-8 字节数，不是 token 数；人设、本轮消息、时间 / 动作信息、图片和协议包装不在这两项正文预算内。

聊天分界线反映经过字节预算后实际选入的近期轮数，完整聊天仍保存在本地。长期召回与这条线独立。

## 关闭不需要的调用

- 只想主动聊天时，关闭周期碎碎念。
- 检查梦话开关；睡觉仍可能触发模型调用。
- 在人设中要求简短回复，前提是符合你的使用习惯。
- 分别检查自动语音、配图和提醒设置，部分功能会使用额外服务。
- 不需要召回和采集时暂停记忆，聊天继续使用近期上下文。

切换音色不会更换角色外形。聊天中记住一句承诺，也不等于创建了提醒；需要提醒时请建立实际待办。

## 算总账

分别记录聊天输入 / 输出、缓存输入、记忆抽取与维护、重试、Embedding，以及缺失的 usage。费用要和成功回答数、事实检查结果一起看。失败请求没有 usage 时应计为未知，不能按免费处理。

[PDF 实验](../explanation/memory-and-cost.md)观察到：

- 原生近期窗口从 10 轮减至 4 轮，聊天输入少了 35.8%，但更难回答窗口外的旧事实。
- 加入记忆后找回了目标事实，也增加了处理开销。
- 固定 1000 轮初始历史、复用 100 次后，已知费用估算比全历史对照低 32.3%。这不是相对原生 10 轮模式的节省，也不是同等质量下的结论。

这些结果用于帮助决定怎样测量，不保证你的场景会有相同比例的节省。
